# DITKit 测试套件

```bash
./tests/run.sh                     # 跑全部（首次会自动合成素材）
./tests/run.sh --list              # 只列用例
./tests/run.sh --filter 裁剪        # 只跑名字或分组里含「裁剪」的
./tests/run.sh --verbose           # 通过的用例也打印输出
./tests/run.sh --refresh-fixtures  # 重新合成素材
```

输出是 TAP 风格的 `ok` / `not ok`，**退出码 0 才算全过**，方便直接接 CI。
失败时每个用例会把自己那段诊断一起打出来，完整日志在 `tests/work/last-run.log`。

前置条件只有三样：先跑过 `./build.sh`、装了 `ffmpeg`/`ffprobe`、有 `python3`（只用标准库）。

## 测试素材：时间码标尺

关键的一条视频叫**标尺**：每 0.5 秒换一种固定纯色，10 色循环，关键帧严格落在整秒。

有了它，「裁剪起点对不对」就不再是「看起来差不多」，而可以变成一条精确断言：

```bash
# 取输出第 0.25 秒那一帧，它在源里对应「起点 + 0.25」秒，
# 应当正好落在某一段色块的正中间 —— 于是可以反推起点有没有取对。
got=$(ruler_second "$out" 0.25)
want=$(ruler_expected 3.75)     # 起点 3.5 + 0.25
expect_eq "$want" "$got" "起点 3.5 处（非关键帧）的颜色段"
```

两个刻意的设计都是有原因的：

- **每段只有 0.5 秒**（短于 1 秒的关键帧间隔）。否则起点正好落在关键帧上，「精确重编码」和「快退到关键帧」出来的结果一样，就区分不出两者了。
- **关掉场景切换插关键帧**（`scenecut=0`）。每 0.5 秒一次硬切会被 x264 当成场景变化而插 IDR，关键帧就不在整秒上了，上面那条假设会失效。

LUT 用的是 **R↔B 通道互换**的 2 点 cube。这个映射是线性的，而 2 点 cube 的三线性插值能精确复现线性映射 —— 所以「输入 (R,G,B) 必须得到 (B,G,R)」是一条硬断言。它同时证明了 LUT 被套用了、而且方向是对的，比「颜色变了没」强得多。旁边还有一条**恒等 LUT**做对照，说明管线本身不偏色。

## 测试素材：音高标尺

音频那条叫**音高标尺**（`tone_ruler.mp4` / `tone_ruler.m4a`）：画面还是时间码标尺，声音则是每 0.5 秒换一个纯音，300 → 400 → … → 1200 Hz 循环。

有两条**互相独立**的路可以断言「提取的区间对不对」：

```bash
# 路 1：与「整段解码」逐样本对齐。起点位置、内容、时长一起验。
"$PYTHON" "$AUDIORANGE" range ref.wav out.wav 1 2
#   -> rate=48000 ch=1 expect=48000 got=48000 offset=0 mad=0.000 maxdiff=0 shift_mad=3314.118

# 路 2：直接量输出某时刻的主音高（Goertzel），对照「源 t 秒应该是第几号」
"$PYTHON" "$AUDIORANGE" tone out.wav 0.6
#   -> hz=600 ratio=7167.0 best_db=60.2 second_hz=500 second_db=-16.9
```

两条都过才算数：路 1 依赖一个参考文件，路 2 不依赖；路 1 的 `offset` 量化起点位置，路 2 直接说「这一段是什么音」。

三个刻意的设计：

- **`mad` 只对无损产物成立**（wav / flac）。参考与产物出自同一次解码，所以正确提取时残差只剩浮点转整数的取整噪声（实测最大 1 个 LSB）。有损重编码之后样本值本来就变了，那种情况请用路 2。
- **`shift_mad` 是反证**：把产物错开半个标尺段再比一次，因为每段换了音高，这一项必须很大（实测 3300 左右）。没有它，`mad≈0` 就分不清是「提对了」还是「这个断言根本分辨不出对错」。
- **`offset` 的容差是一帧**（1024 样本）。同一段解码最多差一个 AAC 帧的定位误差，实测 mp4 源是 0、m4a 源是 256。位置真错了的话偏移会顶到搜索窗口边缘（±0.06 秒）。

`070_audio.sh` 里有一条用例专门拿**错的起点**去比，确认残差会从 0 跳到 3131 —— 那是这套断言自己的自检。

## 测试素材：遮罩合成

遮罩这部分不另造「期望值表」，而是**算出来**。素材侧只声明事实：

```
solid.tsv       128  64  32      整段纯色素材的底色
mask.tsv        ov_full_red   255  0  0
                ov_full_gray  128  128  128
                …
mask_alpha.tsv   ov_half_red  128        半透明图的 alpha
```

用例再按合成公式现场推导期望，例如「中灰叠加、不透明度 50%」：

```bash
base=$(base_rgb)                                     # 128 64 32
gray=$(mask_rgb ov_full_gray)                        # 128 128 128
expect_rgb_near "$(rgb_lerp "$base" "$(rgb_multiply "$base" "$gray")" 0.5)" \
    "$MASK_FULL" 6 "叠中灰 50%"
```

这样断言证明的是**公式对**，而不是「和上次输出一样」。`lib.sh` 里为此提供了 `rgb_lerp` / `rgb_multiply` / `rgb_screen` 三个纯计算助手，以及 `region_rgb`（取某个矩形的均色）。

**位置断言**靠参考区域：画面取左上 `(0,0,40,40)`、正中 `(140,70,40,40)`、右下 `(280,140,40,40)` —— 前两个与后两个正好是 40×40 图层贴到对应位置时覆盖的范围，读数才是纯的（区域越过图层边界就会混进底色，那是在量边界而不是量位置）。

配置成 40×40 的素材（`ov_small_green.png`）就是为了这个：它小于画面，所以「铺满」「等比完整」「原始大小」会给出三种明显不同的读数分布。

**混合模式的单位元**是这套设计的核心，也有专门用例守着：正片叠底配白色画布、滤色配黑色画布，所以「图层盖不到的地方」应当**原样保留**。用例直接断言 `contain` 下四角读数等于底色。

生成半透明 PNG 有个坑：`color=c=0xFF0000@0.5` 和 `0xFF000080` 都**不会**产生透明度，必须走 `-vf "format=rgba,colorchannelmixer=aa=0.5"` 配 `-pix_fmt rgba`。实测 alpha=128。

## 怎么加用例

在一个 case 文件末尾的 `reg` 列表里加一行就行，构建脚本和入口都不用改：

```bash
c_我的新用例() {
    local d
    d=$(fresh_dir my-case)              # 每次给一个干净的工作目录
    out=$(run "$BIN" --cli --trim --start 1 --end 2 --fast --out "$d" -- "$FIX/ruler_a.mp4")
    expect_contains "$out" "结束：共 1，失败 0" "运行结果"
    expect_file "$d/ruler_a_trim.mp4"
}

reg \
    "用例的中文描述"   c_我的新用例
```

可用的断言（都在 `lib.sh` 里，失败时会打印期望与实际）：

| 断言 | 用途 |
|---|---|
| `expect_eq` / `expect_ne` | 相等 / 不等 |
| `expect_contains` / `expect_not_contains` | 输出里有没有某段文字 |
| `expect_file` / `expect_no_file` / `expect_dir` | 文件是否存在 |
| `expect_near` | 数值近似（带容差） |
| `expect_ge` / `expect_le` | 数值上下界 |
| `expect_rgb_near` | 两组 `R G B` 逐通道比较 |
| `expect_audio_range` | 产物就是参考里的那一段（起点偏移 + 残差 + 错位反证），**产物必须是无损格式** |
| `expect_tone_at` | 产物某时刻的主音高是某个 Hz（有损产物也能用） |
| `expect_error <码> <文字> -- <命令...>` | 同时断言退出码与错误提示 |
| `note "..."` | 打一条附注（不影响通过与否） |
| `skip "原因"` | 跳过这个用例（算通过，但标记 SKIP） |

取数与期望值助手：

| 助手 | 用途 |
|---|---|
| `frame_rgb` / `region_rgb` | 取某时刻整帧 / 某个矩形的均值 RGB |
| `base_rgb` / `mask_rgb` / `mask_alpha` | 读素材声明的底色、图片颜色、图片 alpha |
| `rgb_lerp` / `rgb_multiply` / `rgb_screen` | 逐通道线性插值 / 正片叠底 / 滤色，用来推导期望值 |
| `run_mask` | 跑一次 `--cli --mask` |
| `gui_preview_line` / `gui_preview_field` | 取界面自检的 `预览 : ` 诊断行，以及行里某个 `键=` 的值 |
| `band_sec` / `ruler_expected` / `palette_rgb` | 时间码标尺的段长与期望段号 |
| `tone_expected_hz` | 音高标尺在某时刻应该是第几号音高 |

约定：用例函数体里第一个失败的断言就会中止该用例（入口在 `set -e` 的子 shell 里调用它），所以断言直接顺序写即可，不用手工判返回值。

## 覆盖了什么

| 分组 | 覆盖 |
|---|---|
| 命令行 | `--help` 文案；退出码 0/1/2 的三档语义；缺参数值、缺输入、非法时间码、反向区间、未知参数；输入里没有视频时的提示 |
| 时间码 | 纯秒数、`MM:SS`、`HH:MM:SS`、带毫秒、`5s`/`0.5s`/`2m`/`1m30s`/`1h`/`1h2m3s`；六种写法必须等价；片段长度计算；四种非法输入被拒 |
| LUT | 输出编码是 10bit HEVC；恒等 LUT 不改色、交换 LUT 精确换通道；不同规格文件批量；目录递归；`--relative` 落位；三种冲突策略；`--suffix`；**产物不会被当成新素材重复处理**；隐藏文件与隐藏目录被跳过 |
| 裁剪 | 精确模式起点准确（关键帧上 / 非关键帧 / 靠后 / 抽查）；时长与编码；流复制保留源编码并从关键帧起；`--suffix`、`--relative`、批量；先套 LUT 再裁剪；越界时裁到源尾 |
| 音频 | 起点/终点留空各自的语义（整段 / 从头 / 到结尾）；区间精度（两条独立断言 + 抽查）；时间码写法；四种格式的容器与编码、产物里只剩音频流、无损格式不动采样率与声道；码率真的生效；纯音频输入；批量与相对目录；`--suffix`；产物不被当新素材；冲突策略；先裁剪再提取；探针自身能分辨错区间；五种错误路径；源里没有音频流时报失败 |
| 遮罩 | 四种适配方式各自的读数分布（铺满 / 留边 / 按位置贴）；位置只对 `original` 生效；**区域探针能分辨不同位置**（反证）；不透明度按比例混合（含越界夹取）；图片自带 alpha 生效且与不透明度等价；三种混合方式与各自的单位元；**混合在 RGB 空间进行**（逐通道不变）；**混合时未覆盖区域保持原样**；输出规格（HEVC 10bit / `hvc1` / 音频复制 / 时长与尺寸不变）；编码质量真的生效；批量与相对目录；`--suffix`；产物不被当新素材；冲突策略；不同尺寸混批；没有音频的素材；先裁剪再加遮罩；六种错误路径；用法文本列出本页选项 |
| 引擎收尾 | 并发 1 + 8 个文件构造「1 个在跑、7 个排队」，点停止后**排队任务必须被记账为已取消**且引擎真的收尾；不停止时全部跑完并产出 8 个文件；无残留 ffmpeg 进程 |
| 界面 | 四个工具页在深浅两套主题下都能渲染；**顶栏（标题与页切换器）真的画出来了**；页面主体有内容；音频页源信息会报出音频流概况；**遮罩页合成静帧出图**（没选图片时给源画面）；**遮罩页把竖直空间分好**（预览 ≥96、列表 ≥80、列表不压状态行、底部按钮栏不溢出）；**预览源跟着唯一选中项走**（选中多行则退回第一个）；**音频页波形与区间高亮**（含「源里没有音频流」时给说明）；自检诊断信息；干净偏好下能启动 |
| 列表交互 | LUT 拖放框按后缀名把关（视频文件被拒且状态行说明原因、`.cube` 被收下、文件夹被拒）；列表能全选后删除（行数归零、按钮变灰、状态行写明「磁盘上的文件不受影响」）；**列分隔条能拖且拖后不被自动布局覆盖**（带 `NSTableColumnUserResizingMask` 位、宽度真的 +40 并保住）；拖入区就是列表本身（每个工具页只有这一个拖放目标，LUT 页另有一个专收 `.cube` 的拖放框） |

列表类的断言全部走自检诊断行，不碰像素：

```
NSScrollView  x=18 y=491 w=668 h=145  rows=0 w=[224,287,145] mask=[2,3,2]
```

`rows` 用来断言增删，`w` 是列宽（拖分隔条会变），`mask` 是列的 `resizingMask` —— 值里带 `NSTableColumnUserResizingMask`(=2) 这一位才拖得动。用例里对应的取数是 `gui_rows` / `gui_col_w` / `gui_col_masks` / `gui_button_enabled`。

**预览的断言也不碰像素**。预览图是后台跑 ffmpeg 出来的，出图时机不好锁；所以预览的状态经一行诊断暴露出来：

```
预览    : 源=ruler_a.mp4（首个） 640x360 遮罩=ov_full_red.png 构图=stretch/normal/100 时刻=1.000 合成=ok
预览    : 源=tone_ruler.mp4（首个） 波形=ok 区间=00:00:01.000→00:00:03.000 带=167.5+333.0/668.0
```

`源=…（首个 / 选中）` 直接把「按哪条规则挑的源文件」写出来，`合成` / `波形` 是「图真的出没出」的凭证，`带=` 是波形上高亮条的实际绘制位置（区间比例算得对不对，从这几个数上一眼能看出来）。对应的取数是 `gui_preview_line` 与 `gui_preview_field`。

有两条用例是**故意锁定当前行为**的（名字里带「已知问题」）：越界裁剪会产出一个空容器却仍报成功。它们不是期望行为，而是让「有人修好它」这件事能被测试发现 —— 详见 README 的「已知限制」。

## 无头自检（`--selftest`）

界面用例不点鼠标，靠 `--selftest` 起一次真实窗口、注入状态、打印诊断、抓图、退出。
所有注入都走环境变量，所以不会污染用户偏好（用例里仍会先 `defaults_reset`，保证截图可复现）。

```bash
defaults delete local.tools.ditkit
DITKIT_PAGE=3 DITKIT_DROP=a.mp4 DITKIT_IMAGE=logo.png \
  DITKIT_SHOT=/tmp/shot.png ./build/DITKit.app/Contents/MacOS/DITKit --selftest
```

| 变量 | 作用 |
|---|---|
| `DITKIT_APPEARANCE` | `dark` / `light`，强制外观 |
| `DITKIT_PAGE` | 打开第几个工具页（0 起，按 `main.swift` 里 `pages` 的顺序） |
| `DITKIT_DROP` | 往当前页的列表里塞文件，`\|` 分隔多个；目录会递归展开 |
| `DITKIT_LUT` / `DITKIT_LUT_DROP` | 预置 LUT / 模拟往 LUT 拖放框里拖东西（用来验后缀把关） |
| `DITKIT_IMAGE` / `DITKIT_MASK_DROP` | 预置遮罩图片 / 模拟往遮罩拖放框里拖东西 |
| `DITKIT_OVERLAY_FIT` `_BLEND` `_POS` `_OPACITY` `_TIME` | 预置遮罩参数（`stretch` / `multiply` / `br` / `60` / `00:00:03`） |
| `DITKIT_TRIM_START` / `_END`，`DITKIT_AUDIO_START` / `_END` / `_FORMAT` | 预置裁剪与音频页的区间与格式 |
| `DITKIT_LIST_ACTION` | `select-all` / `select:<行号>` / `delete` / `delete-all`，驱动列表 |
| `DITKIT_COLUMN_DRAG` | `<列号>:<加宽量>`，模拟拖一次列分隔条 |
| `DITKIT_AUTOSTART` / `DITKIT_STOP_AFTER` | 自动开始 / N 秒后自动点一次「停止」 |
| `DITKIT_SHOT` / `_DELAY` / `_VIEWCACHE` | 抓图路径 / 抓图前的等待秒数 / 强制走视图缓存 |
| `DITKIT_LINGER` | 抓完继续留在屏幕上 N 秒，方便肉眼确认 |
| `DITKIT_EXIT_WHEN_IDLE` / `DITKIT_TIMEOUT` | 轮询到当前页不忙就退出（带超时），替代「死等固定秒数」 |

自检会把当前页的控件树按 y 排好、连同文本与状态一起打印出来，所以「布局对不对」也能断言 —— 这也是排查布局问题的第一手材料。

## 关于界面截图

界面用例靠自检模式截图，有三条路，按画面完整程度往下退：

| 路径 | 手段 | 依赖 | 画面 |
| --- | --- | --- | --- |
| 1 | 窗口合成（`CGWindowListCreateImage`） | 本进程要有录屏权限 | 最全，含标题栏 |
| 2 | 外部抓图（`screencapture -l <窗口号>`） | 调用方的录屏权限 | 与 1 相同 |
| 3 | 视图缓存（`cacheDisplayInRect:`） | 无 | 兜底，抓不到 layer-backed 控件的文字与底色 |

前两条拿到的都可能是一张纯色图（权限被拒时的表现），所以每张图都要先过一遍「是不是整张同色」的判定，同色就继续往下退。重编会让本进程的签名变，路径 1 的授权随之失效，路径 2 不受影响 —— 那正是加它的原因。

`DITKIT_SHOT_VIEWCACHE=1` 可以强制走 3)，用来单独验证兜底路径。如果三条路都拿不到内容，用例报 SKIP 而不是 FAIL —— 那是环境限制，不是界面问题。但只要拿到图，「顶栏那一条有没有内容」就是硬断言。

## 这两个 bug 是测试守住的

套件里的两条守卫都做过 A/B 反证（把修复退回去，确认用例真的会变红），不是「永远绿」的装饰：

| 退回的修复 | 变红的用例 | 报出的信息 |
|---|---|---|
| `DITEngine.cancel` 不清空排队队列 | 引擎收尾 · LUT 页 / 裁剪页 | `busy 期望=[0] 实际=[1]` |
| `LayoutView` 在 `drawRect:` 里填底色 | 界面 · 顶栏 / 裁剪页 | `期望=[content] 实际=[blank]` |

两次反证里，「不停止时全部跑完」和「页面主体有内容」都保持绿色 —— 说明用例抓到的是那个具体缺陷，而不是随手连坐。
